更新日期：2026-10-30。本文记录本次与用户确认的方向，供后续开发会话沿用。新增需求可以更新本文，不应依据历史原型或“个人娱乐”的定位自行降低画面目标。

## 用户想要的游戏

用户希望得到可安装、供自己玩的完整游戏，暂不以小程序发布为目标。用户主要负责试玩和反馈，开发、素材处理、工程配置和构建由助手完成。

查回早期设计后补充：用户最初明确以手机游玩为主，采用竖屏战斗。Android 是首要运行与性能验证平台；Windows 可以用于开发和桌面版本，不能只根据本机 Windows 环境就把验收目标改成高性能 PC。

用户明确认为当前网页适合验证原型，但画面太简陋，不能作为正式版。预期战斗表现的参照项目是 `C:/code/games/my_zzbx`。即使用户不亲自操作编辑器，也需要按该完成度建设正式表现层。

## 已确定的路线及理由

正式版采用 Cocos Creator 3.8.x，本机已安装版本为 3.8.8。保留独立的 TypeScript 战斗模拟核心，使用 Cocos 承接场景、角色动作、技能特效、UI、音效和目标平台发布。

**FairyGUI 仅用于菜单、养成、弹窗等 UI；战场使用独立的 Cocos 表现层。** 角色、弹丸、技能效果及随单位变化的战场标识不走 FairyGUI。参考项目的战斗完成度需要达到，其运行时架构中可能带来卡顿的设计需要改进。详细边界及验收目标见 [战斗架构与性能要求](battle-architecture.md)。

选择 Cocos 的理由是复用完整的游戏运行时、动画、资源、渲染和发布能力，便于持续制作达到参考项目标准的战斗表现。不是因为必须发布小程序，也不要求用户使用可视化编辑器。

网页的画面上限并不等于目前的观察器。Cocos 也可以用浏览器提供正式画面的试玩预览。已经否定的建议是：因为只供用户自己玩，就继续把简单 Canvas 观察器当正式画面，或给现有简陋网页加桌面外壳作为正式版。

仅把当前原型搬进引擎并不能自动提升质量。角色素材、动作设计、技能演出、命中反馈和场景/UI 仍需按正式标准制作。

- 项目基于已有 Android 战斗客户端继续开发，已具备战斗系统与资源，不能把它的完成度理解成从空白引擎自动生成的效果。
- 角色使用 FairyGUI 动画包、图集和逐帧动画；`tools/art/pack_hero.py` 负责角色资源打包，`art/heroes/angewomon/pack.json` 包含动作帧与时长配置。
- 上一条仅说明参考项目的实现，不是《轮回坛》的技术方案。可以借鉴逐帧素材、挂点、时长与出手帧的设计，正式角色和特效应接入 Cocos 战斗渲染，不复刻 FairyGUI 战场资源/节点结构。
- 待机、移动、普攻、施法、受击、死亡有不同动作。攻击具有逐帧停留和出手时点，画面与弹丸/伤害结算同步。
- 悟空演出同时控制身体姿势、独立武器、方向、伸长与旋转、落地效果和时序，可参考 `offline/sunwukong-runtime.js`、`offline/sunwukong-motion.js`。
- 地面效果、人物、弹丸及覆盖特效按层组织；技能贴图与逐帧变化提供具体的视觉形状。
- Creator 2.2.2 的运行时代码和 FairyGUI 资源包不能直接当成 Creator 3.8.8 工程使用。借鉴动作、素材和运行时组织方法，接入新工程需做适配。

本次参考的是战斗制作质量与方法；用户没有要求《轮回坛》改成 `my_zzbx` 的黑白画风。原有中国神话题材及美术探索仍可作为背景，正式角色与场景风格应结合实际效果继续完善。

## 正式画面的最低交付标准

- 角色要有可辨识的待机、移动、攻击、受击、死亡及招牌技能动作。按动作需求制作逐帧动画或单图变形动画（路线见 [角色动作制作](animation-pipeline.md)，骨骼动画已试过不采用），不机械统一帧数。
- 普攻和技能要有准备、释放/命中、收势或消散的清楚节奏；允许瞬发技能，但表现必须与真实结算时点匹配。
- 武器、弹丸、地面效果、受击反馈和角色动作需要协同；特效大小、方向、范围和结束时间与机制对应。
- 场景、角色、特效、UI 和音效形成统一的完成画面；在实际游戏显示尺寸、正常速度及多单位战斗中检查可读性。
- 静态角色平移、抖动、缩放，以及几何圆圈和文字可以用于调试、占位或辅助反馈，不能单独充当正式动作与核心技能表现。
- 用户通过可试玩版本、动作预览和特效预览提出反馈，无需亲自进入编辑器。资源预览与真实战斗运行应明确区分。
